# Logers.Watch

A Web3 watch-to-earn platform where viewers deposit tokens on-chain, pay as they stream video content, and creators claim earnings on-chain using Merkle proofs generated by the backend.

## Overview

Logers.Watch combines Web2-like streaming UX with Web3 payment rails.

Core idea:

- users deposit supported ERC-20 tokens into the `LogersWatch` contract,
- streaming requests are billed by backend segment logic,
- usage is settled to database state,
- creators receive claim proofs and claim earnings on-chain.

Project maturity:

- feature implementation is complete,
- aggressive real-world testing and full production hardening were not completed,
- treat this repository as a strong demo/prototype baseline.

## Features

### Core Functionality

- User and creator authentication with JWT and cookie support.
- Video upload and DASH processing pipeline.
- Segment-based watch billing with Redis-backed pending deductions.
- On-chain synced user balances (`balance`, `totalConsumed`, pending deductions).
- Creator Merkle proof generation and verification endpoints.

### Blockchain Capabilities

- On-chain user deposits via `deposit` (permit) and `depositWithoutPermit`.
- Creator on-chain claim flow using Merkle proofs.
- Configurable platform fee in contract logic.
- Supported token allowlist controlled by owner.

### Operational Features

- BullMQ-based background video processing worker.
- Scheduled Merkle root updates with idempotent root persistence.
- Admin routes for Merkle trigger/history/active root checks.
- WebSocket billing channel for real-time session and balance updates.

## Smart Contracts

### 1. `LogersWatch.sol`

Main protocol contract in `contracts/src/LogersWatch.sol`.

Key user functions:

- `deposit(token, value, deadline, v, r, s)`
- `depositWithoutPermit(token, value)`

Key creator function:

- `claim(proof, totalEarnings, token)`

Key owner/admin functions:

- `setMerkleRoot(root)`
- `changePlatformFee(newFee)`
- `addCreator(creator)` / `banCreator(creator)`
- `addNewTokenSupport(token)` / `banTokenSupport(token)`

Key getters:

- `getTotaldepositedByUser(user)`
- `getTotalWithdrawnByCreator(creator)`
- `getPlatformFee()`

### 2. Merkle Claim Pipeline

Merkle service in backend:

- computes creator earnings from watch-time and `EARNINGS_RATE_PER_SECOND`,
- generates root + proofs,
- stores active tree and proof rows in DB,
- updates on-chain root when changed.

## Installation

### Prerequisites

- Node.js `>=20`
- Bun `>=1.1`
- Docker + Docker Compose
- Foundry (`forge`, `cast`, `anvil`)
- `ffmpeg` recommended for video processing

### Setup

```bash
# From repository root
cd backend
docker compose up -d

# Backend dependencies and Prisma
bun install
bun run db:generate
bun run db:migrate

# Frontend
cd ../frontend
npm install

# Contracts (optional for local app run, required for contract work)
cd ../contracts
forge build
```

### Environment Variables

Create:

- `backend/.env`
- `frontend/.env.local`

Backend example:

```env
DATABASE_URL="postgresql://logers:logers_secret@localhost:5432/logers_watch"
JWT_SECRET="change-this"
ADMIN_API_KEY="change-this"
REDIS_URL="redis://localhost:6379"
REDIS_HOST="localhost"
REDIS_PORT="6379"
RPC_URL="https://..."
RPC_FALLBACK_URL="https://..."
CHAIN_NAME="sepolia"
LOGERS_WATCH_CONTRACT_ADDRESS="0x..."
SUPPORTED_TOKEN_ADDRESS="0x..."
ADMIN_KEYSTORE_NAME="..."
ADMIN_KEYSTORE_PASSWORD="..."
ENABLE_MERKLE_CRON="true"
MERKLE_UPDATE_CRON="0 * * * *"
EARNINGS_RATE_PER_SECOND="0.00005"
```

Frontend example:

```env
NEXT_PUBLIC_API_URL="http://localhost:3000/api/v1"
NEXT_PUBLIC_PROJECT_ID="walletconnect-project-id"
NEXT_PUBLIC_LOGERS_WATCH_CONTRACT_ADDRESS="0x..."
NEXT_PUBLIC_SUPPORTED_TOKEN_ADDRESS="0x..."
```

## Testing

Current practical status:

- contract testing is available via Foundry,
- backend/frontend test coverage is limited,
- heavy stress and adversarial testing was not fully completed.

Recommended validation flow:

```bash
# Contracts
cd contracts
forge test

# Backend compile/runtime sanity
cd ../backend
bun run dev

# Frontend lint/build checks
cd ../frontend
npm run lint
npm run build
```

End-to-end manual checks:

- creator upload -> processing reaches `READY`,
- user watch session updates balance in real time,
- billing settle updates DB values,
- creator gets valid proof and can claim on-chain.

## Security Considerations

- Admin endpoints require admin API key or admin JWT.
- Creator claim depends on valid active Merkle root and proof.
- Streaming endpoint validates segment names to reduce path traversal risk.
- Merkle updater has in-flight lock to avoid overlapping runs.
- RPC fallback support exists (`RPC_FALLBACK_URL`) for resilience.

Important warning:

- this codebase has not undergone full external security audit.
